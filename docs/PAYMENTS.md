# Payments on the website (Razorpay)

ADDABAAZ Premium is sold **on the website only**. The Android and iOS apps never show a price, a checkout or a
link to one — that is a store-policy requirement (Google Play Payments and App Store guideline 3.1.1) and it
is enforced in code, not just in copy:

| Surface | Behaviour |
| --- | --- |
| Website (`/plans`) | Full checkout through Razorpay when the keys are configured |
| Website, keys missing | Development: an instant, clearly labelled **demo checkout**. Production: prices are listed with “Payments aren’t available right now”, and `POST /api/v1/billing/checkout` answers `501 payments_not_configured` |
| Native app (`window.Capacitor` present) | The buy buttons are **not rendered at all**; the page says plans are bought on the website, and the footer copy avoids any purchase wording. `isNative` gates it in `app/js/views/plans.js` |
| Both | Viewing an existing subscription, invoices and refund requests keeps working everywhere |

Nothing in the app or website breaks when Razorpay is absent: `paymentsFromEnv()` returns `razorpay`,
`mock` (development) or `none`, and every caller handles `none`.

---

## 1. Before you start

* A Razorpay account with your **business KYC** completed (PAN, bank account, GST if registered). Live
  checkout cannot be switched on before Razorpay approves the account.
* Your **GST details**, if you are GST-registered — invoices are generated by ADDABAAZ itself; see
  [BILLING.md](BILLING.md).
* A public HTTPS URL for the API (Razorpay calls the webhook server-to-server).

## 2. Get the API keys

1. Sign in to the [Razorpay Dashboard](https://dashboard.razorpay.com).
2. Switch to **Test mode** (top-right toggle) while you try things out.
3. **Settings → API Keys → Generate key** — copy both values. The secret is shown once.
4. Add them to `.env` and restart the server:

```ini
RAZORPAY_KEY_ID=rzp_test_XXXXXXXXXXXXXX
RAZORPAY_KEY_SECRET=XXXXXXXXXXXXXXXXXXXXXXXX
RAZORPAY_WEBHOOK_SECRET=choose-a-long-random-string
```

Confirm the server picked them up:

```bash
curl -s https://addabaaz.in/api/v1/plans | grep -o '"provider":"[a-z]*"'
# → "provider":"razorpay"
```

While testing, keep using the test keys; when the KYC is approved, generate **live** keys (`rzp_live_…`) and
replace both values. The change takes effect on restart; no code change is needed.

## 3. Configure the webhook (this is what actually activates a plan)

Payments are activated by Razorpay’s webhook, not by the browser returning from checkout — a viewer who
closes the tab after paying still gets their plan.

1. Dashboard → **Settings → Webhooks → Add New Webhook**.
2. **URL**: `https://<your-api-host>/api/v1/payments/webhook`
3. **Secret**: the same string as `RAZORPAY_WEBHOOK_SECRET` above.
4. **Active events**: `payment.captured` (required). `payment.failed` and `refund.processed` are useful but
   optional — failed attempts are recorded from the checkout callback too.
5. Save, then use **Send test webhook** to confirm the endpoint answers `200`.

The endpoint verifies the `X-Razorpay-Signature` header with HMAC-SHA256 over the raw body using the webhook
secret, so a wrong or missing secret simply rejects the call (and logs it). Every delivery is idempotent:
the same payment id can arrive twice without granting two plans.

## 4. Test the flow end to end

1. Sign in on the website with a normal viewer account, open **Plans**, choose the monthly plan.
2. Pay with a Razorpay test card (e.g. `4111 1111 1111 1111`, any future expiry, any CVV) or **UPI → success**.
3. Within a few seconds the plan should show as active on `/account`, and **Admin → Payments** should list the
   payment with a GST invoice.
4. Try the failure paths too: a card Razorpay declines (`4000 0000 0000 0002`), an abandoned checkout, and a
   duplicate webhook (Send test webhook twice) — the second delivery must not extend the plan twice.

## 5. What the customer sees

* **Plans** (`/plans`): one ADDABAAZ Premium card with Monthly/Yearly duration tiles (per-month hint on
  yearly), prices in INR incl. GST, and a single Pay button (*Pay ₹X*, *Extend ₹X* or *Switch to ₹X*
  depending on the account). An Apply Coupon link under the button opens the coupon popup (the button
  then shows the struck-through price); GST billing details are only asked when the server has GST
  enabled. Cancelling the payment window shows a retry screen; a successful payment shows a
  full-screen celebration.
* **Billing** (`/billing`): every payment with its tax invoice / receipt PDF, credit notes for refunds, an
  “Email me the invoice” button and a self-service refund request inside `REFUND_WINDOW_DAYS`.
* **Account**: plan status, expiry date, devices, and how to cancel (there is no auto-renewal: a plan simply
  expires, nothing is charged again).

## 6. Coupons, refunds and GST

| Feature | Where it lives |
| --- | --- |
| Coupons (percentage or flat, usage limits, expiry) | Admin → Coupons; applied in the checkout dialog |
| Refunds | Admin → Refunds (Razorpay dashboard refund, or the self-service request queue) — credit notes are generated automatically |
| GST invoices | `GSTIN`, `GST_LEGAL_NAME`, `BUSINESS_ADDRESS` in `.env`; see [BILLING.md](BILLING.md) |
| Demo checkout | `ALLOW_MOCK_PAYMENTS=true` (staging only — anyone can grant themselves a plan) |

## 7. Store-policy wording (what the apps say)

The apps show, verbatim, on the Plans page:

> Plans are managed on the ADDABAAZ website. Once you’ve subscribed with this account, premium videos unlock
> here automatically.

and in the price note:

> Prices in INR, inclusive of GST. Subscriptions are bought on the ADDABAAZ website, never inside this app —
> your plan unlocks premium video here as soon as the payment is confirmed.

There is **no** purchase button, no external purchase link, no “buy”/“subscribe”/“upgrade” call to action and
no mention of a payment provider in the native build. Reviews for Google Play/App Store should describe the
app as requiring an account; if a reviewer asks how the subscription is bought, the answer is: on the website.
If you ever add in-app purchases, do it through Google Play Billing / StoreKit instead of Razorpay — mixing
them in one app is the usual rejection reason (3.1.1).

## 8. Troubleshooting

| Symptom | Cause / fix |
| --- | --- |
| `/plans` says “Payments aren’t available right now” | `paymentsFromEnv()` returned `none`: keys missing, or only one of the two is set, or the server was not restarted |
| Checkout opens but the plan never activates | Webhook not configured, wrong secret, or the event list does not include `payment.captured`. Check Admin → Errors and Razorpay → Webhooks → deliveries |
| `502` from the checkout API | Razorpay rejected the order (bad key pair, or the account has no live access yet). The message from Razorpay is passed through to the console |
| Invoice shows the wrong GST amount | `BUSINESS_STATE`/`GSTIN` unset. See [BILLING.md](BILLING.md) |
| Refund requests are hidden | `REFUND_WINDOW_DAYS=0` disables self-service requests |
| Buy buttons missing on the phone app | Correct and intentional — the native build never offers checkout |
